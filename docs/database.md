# Database

PostgreSQL is the persistent data store. Access uses parameterized SQL through `pg`, with no ORM.

## Tables

- `customers`
- `staff`
- `products`
- `orders`
- `order_items`
- `return_requests`
- `refunds`
- `idempotency_keys`

## Relationships

```text
Customer
   │
   └── Orders
          │
          ├── Order Items   (snapshot of product name and price)
          │
          └── Return Requests
                    │
                    └── Refunds

Products  (catalog; read when an order is placed)
```

- Orders use UUID primary keys generated by PostgreSQL.
- `order_items` uses `(order_id, product_id)` as its composite primary key.
- `return_requests` references an order item through `(order_id, product_id)`.
- Orders use `ON DELETE CASCADE` for their order items.
- Refunds have a uniqueness rule that applies only to active refunds, so a failed refund can be retried.
- Idempotency keys are unique per `(user_id, idempotency_key)`.

## Products and server-side pricing

The server never accepts prices from the client. When an order is placed, it looks up each requested product in the `products` table and copies the current name and unit price into the order's items.

- Fields such as `name` or `unitPrice` sent by a client are ignored.
- Unknown or inactive products are rejected with `400`.
- Order items are a **snapshot**: changing a product's price later does not change existing orders. For that reason `order_items` has no foreign key to `products`.
- Quantities must be whole numbers from 1 to 500.

## Migrations

Migration files live in `src/db/migrations/`, each with an `_up.sql` and a `_down.sql` file:

| Migration | Purpose |
| --- | --- |
| 001 | Initial schema |
| 002 | Authentication (customers and staff) |
| 003 | Idempotency keys |
| 004 | Fix the idempotency constraint |
| 005 | Allow refund retry after failure |
| 006 | Products table |

The runner in `src/db/migrate.ts` has two limits to be aware of:

1. It keeps its own list of files, so a new migration must be added to both the up and down lists.
2. It does not record which migrations have run. `migrate:up` replays every migration, so it only works on an **empty** database.

To add a migration to an existing database, apply only the new file:

```bash
psql "$DATABASE_URL" -f src/db/migrations/006_add_products_up.sql
```

For disposable databases, such as the test database, you can reset with `migrate:down` followed by `migrate:up`.
